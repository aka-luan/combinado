Lesson 0001 · Email OTP

OTP is not the session

You already know session cookies keep someone logged in. Today’s win: see where a one-time code stops and the session begins.

One idea

An OTP is a short-lived proof used at login. A session secret is what the server issues after that proof succeeds so later requests stay authenticated. NIST calls the latter a session secret; OWASP requires OTPs to be short-lived and single-use.

you app auth server email | | | | |-- email -->| | | | |-- request OTP->| | | | |-- send code --->| | | | | |<- "check email" -----------| | | | | | |-- 6 digits ---------------->| | | |-- verify OTP -->| | | |<- session -----| | | | (cookie/token)| | | | | | |==== later requests use SESSION, not the code =====>
Combinado hook Issue #2 follows exactly this: signInWithOtp sends the code; verifyOtp returns a session; the PWA then persists that session. The digits never become the long-term credential. — Supabase passwordless guide

Why the split matters

  • OTP dies fast (minutes). Guessing a 6-digit code is only dangerous if you can try forever — so TTL + attempt limits matter.
  • Session lasts (hours/days, with refresh). That’s the cookie world you already know: continuity without retyping a code every request.
  • If an app “logged you in” by storing the OTP itself, a leaked inbox screenshot could impersonate you for as long as that value lived — the wrong lifetime for the wrong job.
